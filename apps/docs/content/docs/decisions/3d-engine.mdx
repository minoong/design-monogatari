## 결정

차량 3D는 **Three.js와 React Three Fiber**를 그대로 써요. Babylon.js로 바꾸지 않아요.

## 왜 비교했나

프론트엔드 채용에서 3D 경험이 어느 라이브러리 기준으로 평가되는지가 궁금했어요. Babylon.js를 요구하는 공고가 더 많다는 이야기가 있어서 생태계 지표를 직접 재 봤어요.

## 측정 (2026-10-12)

| 지표                          | Three.js 쪽                     | Babylon.js 쪽                               |
| ----------------------------- | ------------------------------- | ------------------------------------------- |
| 핵심 패키지 월 다운로드 (npm) | `three` 83,509,977              | `@babylonjs/core` 1,738,019                 |
| React 바인딩 월 다운로드      | `@react-three/fiber` 25,514,308 | `react-babylonjs` 15,530, `reactylon` 1,118 |
| GitHub 별                     | `mrdoob/three.js` 116,289       | `BabylonJS/Babylon.js` 26,156               |
| 라이선스                      | MIT                             | Apache-2.0                                  |

핵심 패키지 기준으로 Three.js 쪽이 약 **48배** 커요. React 바인딩은 약 1,600배 차이가 나요.

## 측정하지 못한 것

채용 공고의 실제 수와 요구 기술은 직접 세지 못했어요. 그래서 "Babylon.js 공고가 더 많다"는 말을 확인하지도 반박하지도 못해요. 이 결정은 생태계 규모와 이미 구현된 코드의 재사용성에 근거한 것이에요.

## 이유

1. **이미 구현한 것이 있어요.** 도장 색(MeshPhysicalMaterial 클리어코트), HDR 조명, 그림자, 반쪽 메시 미러링, GSAP 스크롤 연동이 Three.js로 동작해요. 엔진을 바꾸면 이 코드를 처음부터 다시 써야 해요.
2. **React 생태계가 훨씬 커요.** 이 레포는 React 19 기반이고, 바인딩의 유지보수와 예제, 질문과 답변이 Three.js 쪽에 압도적으로 많아요.
3. **Babylon.js의 장점은 이 프로젝트에 결정적이지 않아요.** 내장 Inspector, TypeScript 우선 설계, 제품 구성기용 PBR 기능은 매력적이지만 이미 Three.js로 같은 결과를 냈어요.

## 되돌릴 조건

3D 코드를 별도 패키지(`@repo/vehicle-3d`)로 옮겨서 앱은 그 패키지의 작은 API만 쓰게 할 계획이에요(다음 작업). 그러면 나중에 엔진을 바꿔야 할 때 패키지 안쪽만 바꾸면 돼요.

## 라이선스 메모

BMW X5 G05 모델은 BMW Car IT의 CC BY 4.0 공개본이에요. 앱에 포함하면 제작자, 출처, 라이선스, 보증 부인, 수정 사실을 표기하고 BMW 상표가 허가된 것이 아님을 밝혀요. 자세한 표기는 레포의 `.storybook/public/models/README.md`에 있어요.
