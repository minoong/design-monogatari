하네스는 한 번에 완성되지 않았습니다. 작업하면서 **빠뜨린 것이 나올 때마다** 점검을 늘렸습니다. 여기에는 그 사례와 로그의 실제 수치만 적고, 일어나지 않은 일은 쓰지 않습니다.

## 빠진 것과 보탠 것

| 무엇이 빠졌나                                                                                                       | 어떻게 드러났나                                                                                                                                                                                                                                                                           | 무엇을 보탰나                                                                                                                                                         |
| ------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 공식 문서를 확인하라는 규칙을 글로만 적어서 건너뛰었다                                                              | 사용자가 "터보레포나, 다른 공식 문서 같은 것들은 구현할 때 참고하지 않나?"라고 물었다                                                                                                                                                                                                     | `docs-consult` 훅(고치기 직전 알림, 주제당 한 번), `docs-researcher` 에이전트, `official-docs` 스킬                                                                   |
| 컴포넌트를 만들고 레지스트리 항목이나 문서를 빠뜨려도 어떤 검사도 실패하지 않았다                                   | 계획 단계의 감사에서 확인                                                                                                                                                                                                                                                                 | `pnpm component:new`, `components:check`(`verify`에 포함), `component-check` 훅                                                                                       |
| QA가 동작과 대비만 보고 같은 줄에 놓인 버튼의 모양 차이를 놓쳤다                                                    | 사용자가 "견적링크복사, pdf 저장 버튼 모양이 다르잖아"라고 짚었다. 원인은 `CopyButton`이 `Button`과 다른 기본 크기를 가진 것이었다                                                                                                                                                        | `ui-verifier`의 일관성 점검(나란히 놓인 컨트롤의 높이, 모서리, 글자 크기와 굵기를 계산된 값으로 비교), `design-reviewer` 에이전트(래퍼의 기본값을 코드에서 비교)      |
| 아이콘만 있는 버튼에서 아이콘이 5px 치우친 것을 놓쳤다                                                              | 사용자가 Storybook 링크로 짚었다. 아이콘에 붙은 표식이 한쪽 여백을 만들고 있었다                                                                                                                                                                                                          | "컨트롤 안쪽 점검": 아이콘 중심과 버튼 중심의 차이, 아이콘과 글자 사이 간격, 묶음의 좌우 여백                                                                         |
| 화면에서 숨긴 글자가 문서 스크롤을 늘려 스크롤바가 두 개 생겼다                                                     | 사용자가 "스크롤이 왜 2개가 생기지?"라고 물었고, 스크롤되는 요소를 모두 열거해서 원인을 찾았다                                                                                                                                                                                            | 일관성 점검에 스크롤바와 넘침 요소, 스크롤 영역을 벗어나는 `position: absolute` 요소의 열거를 포함                                                                    |
| 테마 전환 버튼의 문구가 바뀌며 헤더가 밀렸다                                                                        | 사용자가 "라이트, 다크 전환 버튼 누르면 헤더들 위치라고 해야하나? 바뀌는데?"라고 짚었다. 버튼 폭이 "다크" 50px에서 "라이트" 62px로 달라져 견적 요약 버튼이 12px, 단계 막대가 6px 밀렸다                                                                                                   | `ui-verifier`의 상태 전환 이동 점검(전환 전후 이웃 요소의 위치를 폭별로 재서 변화량을 0까지 포함해 보고). 고친 뒤 여섯 폭 모두 변화량 0                               |
| `registry:check`가 실패한 채로 커밋과 PR까지 진행했다                                                               | 린트 자동 수정이 파일을 바꾼 뒤 레지스트리를 다시 만들지 않았다                                                                                                                                                                                                                           | 검증이 통과한 것을 확인한 뒤에만 커밋하는 규칙(`pnpm verify`가 성공일 때만 다음 단계)                                                                                 |
| 서브에이전트가 한도나 멈춤으로 끊겼다                                                                               | 긴 검증이 11분 동안 출력 없이 멈췄다                                                                                                                                                                                                                                                      | 작은 범위로 나눠 재실행, 약 10분 안에 부분 결과를 먼저 보내라는 규칙                                                                                                  |
| 새 에이전트 정의가 실행 중인 세션에 올라오지 않았다                                                                 | `design-reviewer`를 만든 직후 호출하니 "Agent type 'design-reviewer' not found" 오류가 났다                                                                                                                                                                                               | 같은 점검표를 일반 에이전트에 직접 지시해서 사용했고, 세션을 다시 시작해야 반영된다는 점을 문서에 적음                                                                |
| 코드를 바꾼 뒤 브라우저에서 열어 보지 않고 검증을 맡겨서, 화면이 아예 안 뜨는 결함을 검증 에이전트가 처음 알려 줬다 | 내장 색을 칠하는 코드가 표준 재질을 `MeshPhysicalMaterial.copy`에 그대로 넘겨 3D가 로드 때 오류로 멈췄고, 에이전트가 "색 확인을 하나도 못 했다"고 돌려보냈다. 비슷한 시기에 켜 둔 Storybook 개발 서버가 새로 추가한 패키지 export를 읽지 못해 3D 스토리가 모두 로드에 실패했다            | `ui-verifier`에 "처음 로드 확인" 단계(렌더되는지, 콘솔 오류 0, 실패하면 스택을 보고하고 멈춤, 패키지 export나 의존성을 바꿨으면 개발 서버 재시작 여부)를 맨 앞에 추가 |
| 위아래 시선 한계를 거꾸로 걸었는데 한참 뒤에야 알았다                                                               | 한계를 17°에서 11°로 바꿨는데 검증 화면이 똑같았다. OrbitControls의 각도는 조준점에서 본 카메라의 각도라 아래를 보는 쪽이 최소값인데 반대로 걸었던 것이다                                                                                                                                 | 같은 정의 값을 바꿨는데 측정이 변하지 않으면 "적용이 안 됐거나 방향이 틀렸다"고 먼저 의심해 보고하는 규칙을 `ui-verifier`에 추가                                      |
| 단계를 떠날 때만 확인하고 돌아오는 경우는 확인하지 않았다                                                           | 사용자가 "휠 단계인데 시점 버튼은 시트가 눌려 있다"고 짚었다. 직접 고른 시점을 단계에 묶어 기억만 하고 지우지 않아서, 그 단계로 돌아오면 예전 선택이 되살아났다                                                                                                                           | 상태가 단계, 탭, 패키지에 묶이면 "갔다가 돌아오기"까지 확인하도록 `ui-verifier`에 추가                                                                                |
| 한쪽에서 좋아 보이게 고쳤다가 반대쪽이 깨졌다                                                                       | 닫은 선루프의 안쪽 틈을 덮으려고 안쪽 판을 12cm 키웠더니 안쪽은 나아졌지만 지붕 곡면을 뚫고 올라와 바깥에서 검은 파편(체감 5/5)으로 보였다. "도장 밑에 가려질 것"이라는 가정이 틀렸다                                                                                                     | 안과 밖 양쪽에서 확인하는 것을 `ui-verifier` 작업 지시에 넣었고, 키울 수 있는 한계를 `AGENTS.md`에 적었다                                                             |
| 접근성·디자인 리뷰를 건너뛰고 기능을 쌓았다                                                                         | 시점 버튼, 선루프, 캘리퍼, 내장 색을 PR 여섯 개에 걸쳐 만드는 동안 두 리뷰어를 돌리지 않았고, 나중에 한 번에 돌리자 방향 버튼이 없어 드래그만 가능한 점, 방향키로 비활성 행을 지나면 안내 창이 열리는 점, 눌린 버튼의 포커스 링이 사라지는 점, 눌림 표시가 여섯 군데에 복사된 점이 나왔다 | 리뷰어 단계는 규칙에 이미 있었지만 강제 장치가 없어 건너뛰었다. 강제 장치는 아직 없다(아래 "아직 비어 있는 부분")                                                     |
| 조사를 맡긴 에이전트가 검색 한 번으로 한 제조사만 확인하고 나머지는 기억으로 채웠다                                 | 첫 보고에 BMW 외에는 "미확인(출처 없음)"이 달려 있었다                                                                                                                                                                                                                                    | 제조사별로 나눠 다시 조사하게 하고, 보고서가 "확인(출처 주소)"과 "미확인"을 나누도록 요구했다. 한국 시장 가격과 벤츠 일반 트림 색은 끝내 찾지 못해 PR에 그렇게 적었다 |
| 측정 작업이 사용자의 컴퓨터에 부하를 줄 뻔했다                                                                      | 프로덕션 서버를 새로 띄우고 여러 번 반복 측정과 CPU 제한까지 시킬 계획이었는데, 사용자가 "컴퓨터에 부하가 걸린다"며 중단시켰다. 서버는 CPU 0%였고, 부하는 열려 있던 3D 탭이 초당 60번씩 계속 다시 그리는 것으로 보인다(추정)                                                              | 시킨 일이 기계에 주는 부하를 먼저 알리고 범위를 줄이도록 `ui-verifier`의 예산 항목에 추가. 3D의 상시 렌더링은 아직 고치지 않았다                                      |

## 훅 로그의 실제 수치

다음은 `.claude/logs/hook-events.jsonl` 전체를 `decision:reason`별로 센 값입니다. 2026-10-11부터 2026-10-17까지 세션 3개, 이벤트 411건입니다(`pnpm harness:trace`가 같은 로그를 요약합니다).

| 항목                           | 횟수 | 의미                                                       |
| ------------------------------ | ---- | ---------------------------------------------------------- |
| `allow:instr_path_glob_match`  | 195  | 경로 한정 규칙이 해당 파일을 열 때 올라온 횟수             |
| `mark:playwright_used`         | 81   | 브라우저 도구를 쓴 기록                                    |
| `allow:instr_nested_traversal` | 38   | 하위 폴더의 지침이 올라온 횟수                             |
| `allow:instr_include`          | 36   | `@AGENTS.md` 같은 포함으로 올라온 횟수                     |
| `allow:instr_compact`          | 18   | 대화 압축 뒤 지침이 다시 올라온 횟수                       |
| `allow:instr_session_start`    | 12   | 세션 시작 때 올라온 횟수                                   |
| `allow:subagent_not_editor`    | 6    | 파일을 고치지 않는 서브에이전트라 종료를 막지 않은 횟수    |
| `mark:ui_edit`                 | 4    | 화면에 영향을 주는 편집을 표시함                           |
| `mark:verify_passed`           | 4    | `pnpm verify` 통과를 기록                                  |
| `skip:verify_failed`           | 1    | `pnpm verify`가 실패해서 통과로 기록하지 않음              |
| `mark:docs_*`                  | 5    | 문서 확인 기록(Turborepo, Motion, Radix, React, Next 각 1) |
| `nudge:ui_edit_first`          | 2    | 검증 전에 편집했다고 알림                                  |
| `nudge:component_incomplete`   | 1    | 컴포넌트 편집 직후 빠진 항목을 알림                        |
| `allow:dod_satisfied`          | 2    | 종료할 때 조건이 충족되어 통과시킴                         |

로그의 `ui_edit`은 4건뿐인데 실제로는 이 기간에 화면을 훨씬 많이 고쳤습니다. 로그는 상태가 바뀔 때만 적는 것으로 보여서, 이 숫자를 "편집 횟수"로 읽으면 안 됩니다.

<Callout type="warn" title="이 로그에는 종료가 차단된 사례가 없습니다">
  `Stop` 훅이 종료를 막은 기록(`block`)은 이 로그에 없습니다. 검증을 먼저 끝내고 종료한 경우만 남아
  있어서, "막혔다가 고친 뒤 통과한" 이야기는 이 로그로 증명하지 못합니다. 차단 동작이 있다는 것과
  실제로 막은 기록이 있다는 것은 다른 말이므로 구분해서 적습니다.
</Callout>

## 이번 기간에 새로 알게 된 것

- **3D는 가만히 있을 때 그리지 않게 고쳤습니다(`frameloop="demand"`).** 효과를 확인한 방법은 WebGL 그리기 호출을 세는 것입니다(유휴 5초 0회, 조작 뒤 0으로 복귀). 움직임이 이어지는 곳(카메라 이동, 선루프, 관성)이 스스로 다시 그리기를 요청하지 않으면 중간에 멈추므로, 새 애니메이션은 이 측정이 규칙입니다.
- **어색함은 숫자로 쪼개야 고쳐집니다.** "닫힐 때 중간에서 사라진다", "놓으면 위로 튄다", "처음 몇 픽셀은 안 따라온다"는 모두 프레임마다 위치와 불투명도를 재서 원인(투명도가 먼저 0이 됨, 모션이 제자리로 되돌리는 스프링을 먼저 시작함, 터치 시작 거리 15px)을 찾았습니다. 눈으로 본 인상만으로 고치면 같은 문제를 두 번 고치게 됩니다.
- **한계는 적기 전에 시도합니다.** 사용자가 "이건 지금 확인할 수 있는 거 아니야?"라고 되물은 세 가지(다크 윤곽 대비, 18px 건너뜀, 콜백 호출)는 모두 측정해서 고쳤습니다. 실제 기기 터치와 iOS 고무줄 효과만 자동 확인으로 볼 수 없는 한계로 남깁니다.
- **지시 파일끼리 어긋납니다.** 점검해 보니 루트 `AGENTS.md`와 `verify` 스킬은 "요청하지 않으면 커밋하지 않는다", `CLAUDE.md`와 규칙은 "검증 뒤 에이전트가 직접 커밋한다"라고 서로 반대로 적혀 있었습니다. 훅 안내 문구도 같았습니다. 한 곳을 정본으로 두고 나머지를 맞췄습니다.
- **서브에이전트는 한도에 걸릴 수 있습니다.** 긴 검증 도중 세션 사용 한도에 걸려 부분 결과만 돌아온 적이 있고, 같은 에이전트를 이어서(SendMessage) 끝냈습니다. 검증 요청에 범위와 시간을 적고, 3D 페이지 로드 횟수를 제한합니다.
- **읽기 전용 리뷰어에 `memory: project`를 켜면 쓰기 도구가 자동으로 생깁니다**(공식 문서). 본문의 "수정하지 않는다"는 약속일 뿐 강제가 아니라서, 점검 때 실제로 수정하지 않았는지 확인했습니다.
- **`pnpm verify`는 유효한 코드이면 통과시킵니다.** JSX 안에 `//` 주석을 그대로 써서 모든 `PackageRow` 위에 그 문장이 화면에 찍혔는데, 린트와 타입과 빌드가 모두 통과했습니다. 브라우저 검증이 잡았고, 같은 실수를 막는 내장 ESLint 규칙(`no-restricted-syntax`, 새 의존성 없음)을 `@repo/eslint-config`에 넣었습니다.
- **검증 조건이 좁으면 결함이 빠져나갑니다.** 펼침 애니메이션 검증은 열기 직전에 창 크기를 정한 경우만 보았고, 열어 둔 채 글꼴을 키우면 목록이 75px에 고정돼 잘리는 결함은 "확인하지 못한 항목"을 다시 측정하다가 찾았습니다. 보고서에 확인하지 못한 항목을 적어 두고 다음에 실제로 측정하는 순서가 도움이 되었습니다.
- **켜 둔 개발 서버가 오래된 CSS를 낼 수 있습니다.** 새로 만든 컴포넌트의 클래스가 반영되지 않은 Storybook에서 선택 표시가 엉뚱한 곳에 보였습니다. 검증 에이전트가 서버를 새로 띄워 측정했고, 사람이 볼 때도 서버를 재시작해야 한다고 알렸습니다.
- **검증 도구가 끊기면 같은 시도를 반복하지 않습니다.** 컴퓨터가 잠들었다 깬 뒤 서브에이전트의 Playwright MCP가 `CONNECT_TIMEOUT`으로 계속 실패했고(패키지와 네트워크는 정상), VS Code 세션을 다시 열자 복구됐습니다. 서브에이전트에 붙는 MCP는 에이전트가 시작될 때 연결되므로 메인에서 고칠 수 없습니다.
- **대량 조사는 묶음으로 나눕니다.** React Bits와 Animate UI의 컴포넌트 약 370개를 12~20개씩 묶어 `ui-verifier`로 직접 조작했고, 보고 파일을 일찍 만들어 덧붙이게 해서 끊겨도 진행이 남았습니다. 사이트 코드는 옮기지 않았습니다(React Bits는 상업적 재배포를 금지하는 Commons Clause 조건이 붙은 MIT). 채택된 아이디어는 토스트 밀어 닫기, 펼침 높이 전환, 세그먼트 알약이고, 대부분의 배경과 커서 효과는 감소 모션을 무시하거나 키보드·터치 대안이 없어 쓰지 않았습니다.

## 아직 비어 있는 부분

- 접근성·디자인 리뷰어 단계를 강제하는 훅이 없습니다. 이번에 건너뛴 것이 그 증거입니다.
- 훅이 알려 주는 것(`docs-consult`, `component-check`)이 실제로 행동을 바꿨는지는 로그의 횟수로는 알 수 없습니다.
- 스크린 리더와 실제 터치 기기는 자동 확인으로 볼 수 없어서, 접근성 점검은 코드를 읽는 리뷰와 계산된 값 확인까지만 합니다.
- 서브에이전트가 만든 보고의 정확도를 따로 측정하지는 않습니다. 중요한 주장은 수치(계산된 값)나 스크린샷 경로가 붙은 것만 받아들입니다.
