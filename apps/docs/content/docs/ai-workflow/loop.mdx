## 컴포넌트 루프

`@repo/ui` 컴포넌트를 만들거나 공개 API를 바꿀 때의 순서입니다. `create-component` 스킬이 이 순서를 따라갑니다.

```text
정독(DESIGN.md, 비슷한 컴포넌트)
  → pnpm component:new <이름>     스토리, 예시, 문서 페이지, 레지스트리 항목, DESIGN.md 뼈대 (모두 TODO 표시)
  → 구현 → 스토리 → 예시와 문서 → DESIGN.md
  → pnpm registry:sync            레지스트리 복사본 생성 (손으로 고치지 않음)
  → pnpm components:check         빠진 것과 남은 TODO가 있으면 실패
  → design-reviewer, a11y-reviewer   읽기 전용 코드 리뷰
  → ui-verifier                   라이트/다크 브라우저 확인 + 일관성 점검
  → pnpm verify                   형식, 레지스트리, 컴포넌트, 문구 톤, 린트, 타입, 테스트, 빌드
```

## 앱 화면 루프

`apps/web` 화면을 바꿀 때는 규칙이 데이터와 코드로 먼저 정리되어 있습니다. 견적 규칙은 `model/`의 순수 TypeScript이고, 화면은 그 결과(`effects`)를 그대로 그립니다. 그래서 순서는 이렇습니다.

1. 규칙이나 계산이 바뀌면 `model/`에서 먼저 바꾸고 테스트를 추가합니다.
2. 화면은 모델이 돌려준 효과를 알림, 확인 창, 차단 창, 제안 창으로 보여 줍니다. 선택을 조용히 바꾸지 않습니다.
3. `design-reviewer`로 코드의 일관성을 보고, `ui-verifier`가 여러 폭(1920에서 390까지)과 라이트, 다크에서 확인합니다.
4. 성능은 실제 빌드를 띄워 측정합니다(개발 서버의 수치는 쓰지 않습니다).

## PR 루프

| 순서 | 내용                                                                                  |
| ---- | ------------------------------------------------------------------------------------- |
| 1    | `main`에서 `feat/`, `fix/`, `chore/` 브랜치를 만든다. `main`에는 직접 커밋하지 않는다 |
| 2    | 변경한 뒤 `pnpm verify`가 통과한 것을 확인한다. **실패하면 커밋하지 않는다**          |
| 3    | 한글 Conventional Commit으로 커밋한다. 본문에 배경, 변경 이유, 검증, 한계를 쓴다      |
| 4    | push하고 PR을 연다. 제목과 본문은 한글, 테스트 계획에 `pnpm verify`를 쓴다            |
| 5    | PR은 한 번에 하나씩. 사용자가 머지했다고 알리면 `main`을 동기화하고 다음으로 넘어간다 |
| 6    | `main`에 직접 push, force push, 브랜치 삭제는 요청이 없으면 하지 않는다               |

## 각 단계가 잡는 것

| 장치               | 잡는 것                                                                | 못 잡는 것                                               |
| ------------------ | ---------------------------------------------------------------------- | -------------------------------------------------------- |
| `components:check` | 스토리, 문서, 예시, 레지스트리 항목, `DESIGN.md` 누락과 남은 TODO      | 내용이 맞는지                                            |
| `registry:check`   | 원본과 레지스트리 복사본의 차이                                        | 소비자가 실제로 설치되는지(CI의 소비자 설치 검사가 맡음) |
| `copy:check`       | 해요체, 은행 예시 같은 문구 톤 위반                                    | 어색한 문장                                              |
| 린트와 타입        | 접근성 규칙 일부, Tailwind 클래스 충돌, 타입                           | 실제 모양                                                |
| 모델 테스트        | 가격 합산, 규칙 종류별 동작, URL 왕복                                  | 화면                                                     |
| `design-reviewer`  | 래퍼 기본값 불일치, 형제 컨트롤 크기, 아이콘 위치 표식                 | 실제 렌더링                                              |
| `a11y-reviewer`    | 이름, 키보드, 초점, 색 의존, 모션                                      | 실제 스크린 리더 동작                                    |
| `ui-verifier`      | 계산된 크기와 간격, 정렬, 스크롤바, 라이트와 다크, 폭별 레이아웃, 콘솔 | GPU 합성, 실제 터치 기기, 스크린 리더                    |
| `Stop` 훅          | UI를 고치고 검증 없이 끝내는 것                                        | 검증의 질                                                |

마지막 열이 중요합니다. **어떤 장치도 전부를 잡지 못하고**, 그래서 못 잡은 것이 나올 때마다 점검을 보탰습니다. 그 과정은 [개선 기록](/docs/ai-workflow/retrospective)에 있습니다.
